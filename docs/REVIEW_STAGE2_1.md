# Ревью: `migrations/001_init.sql` + `rag/embedder.py`

Общая оценка: схема и структура модуля правильные, интерфейс `EmbedResult`
менять не придётся. Но есть два дефекта, из-за которых sparse-поиск будет
работать неверно, и одно фактически неверное утверждение в комментарии.

---

## 🔴 БЛОКИРУЮЩЕЕ 1 — `_to_token_ids` неверно интерпретирует выход FlagEmbedding

**Файл:** `rag/embedder.py`, метод `_to_token_ids`

Комментарий в коде утверждает: «FlagEmbedding v1 возвращает `lexical_weights`
как `{token_string: weight}`». **Это не так.**

Исходный код FlagEmbedding (`_process_token_weights`):

```python
for w, idx in zip(token_weights, input_ids):
    if idx not in unused_tokens and w > 0:
        idx = str(idx)          # ← str(token_id), а НЕ строка токена
        if w > result[idx]:
            result[idx] = w
```

Ключи — это **строковые представления token_id**: `"6"`, `"12345"`.
Косвенное доказательство есть и в самом API: у `BGEM3FlagModel` существует метод
`convert_id_to_token(lexical_weights)`, который делает `tokenizer.decode([int(id)])`.
Он не был бы нужен, если бы ключи уже были токенами.

**Что делает текущий код:** `tokenizer.convert_tokens_to_ids("6")` ищет в словаре
литерал `"6"` как токен. В словаре XLM-RoBERTa id 6 — это какой-то частотный
sentencepiece-фрагмент, а токен `"6"` лежит совсем по другому индексу.

**Последствие — самое неприятное из возможных: ничего не падает.**
Исключения нет, вектор строится, вставка проходит. Просто индексы разрежённого
вектора не соответствуют токенам. Часть весов уходит в `unk` и отбрасывается
фильтром, остальные встают не на свои места. Sparse-поиск деградирует до шума,
и заметить это можно только по метрикам golden set.

Бьёт это ровно по тому, ради чего sparse и добавлялся: точное совпадение
номеров деталей вроде `1U-5490`.

**Исправление:**

```python
def _to_token_ids(self, lexical_weights: dict) -> dict[int, float]:
    """
    Конвертировать выход FlagEmbedding в {pgvector_index: weight}.

    FlagEmbedding отдаёт {str(token_id): weight} — именно ID, а не токены
    (см. _process_token_weights и наличие метода convert_id_to_token).
    Дополнительно сдвигаем на +1: индексы sparsevec в pgvector 1-based
    («indices start at 1 like SQL arrays»), а token_id 0-based.
    Диапазон 0..250001 → 1..250002, ровно в размерность SPARSEVEC(250002).
    """
    result: dict[int, float] = {}
    for key, weight in lexical_weights.items():
        w = float(weight)
        if w <= 0:
            continue
        try:
            tid = int(key)          # ключ уже есть token_id
        except (TypeError, ValueError):
            continue
        if not 0 <= tid < VOCAB_SIZE:
            continue
        idx = tid + 1               # ← 1-based индексация pgvector
        if result.get(idx, 0.0) < w:
            result[idx] = w
    return result
```

Важно: сдвиг `+1` должен применяться **одинаково при индексации и при запросе**.
Раз обе стороны идут через этот метод — инвариант соблюдён автоматически.

## 🔴 БЛОКИРУЮЩЕЕ 2 — индексы `sparsevec` в pgvector 1-based

**Файлы:** `rag/embedder.py` (`_to_token_ids`, `sparse_to_pgvector_literal`)

Документация pgvector: «The format is `{index1:value1,...}/dimensions` and
**indices start at 1 like SQL arrays**».

Token id `0` (в XLM-RoBERTa это `<s>`) дал бы литерал `{0:...}` — pgvector такое
отклонит. Сейчас спасает только то, что FlagEmbedding исключает спецтокены,
то есть код держится на побочном эффекте чужой библиотеки. Фикс выше это закрывает.

Заодно про пустой вектор:

```python
if not sparse:
    return f"{{1:0.0}}/{VOCAB_SIZE}"     # ← явный ноль
```

Явные нули в sparsevec — сомнительный ввод, pgvector их хранить не должен.
Надёжнее пустой вектор:

```python
if not sparse:
    return f"{{}}/{VOCAB_SIZE}"
```

Проверьте оба варианта одним запросом, прежде чем закладывать:

```sql
SELECT '{}/250002'::sparsevec, '{1:0.0}/250002'::sparsevec;
```

## 🟡 НЕВЕРНОЕ УТВЕРЖДЕНИЕ — HNSW для `sparsevec` поддерживается

**Файл:** `migrations/001_init.sql`, строки 75–77

> `-- SPARSEVEC: pgvector ≤ 0.8 не поддерживает HNSW/IVFFlat для sparsevec.`

HNSW для `sparsevec` **поддерживается** начиная с 0.7.0, есть класс операторов
`sparsevec_ip_ops`. Не поддерживается только IVFFlat.

Настоящее ограничение другое и куда интереснее:
**HNSW по sparsevec работает лишь до 1 000 ненулевых элементов в векторе**
(сам тип хранит до 16 000, но индекс — 1 000).

Почему это важно именно вам: число ненулевых у bge-m3 равно числу уникальных
токенов в тексте. При медиане чанка 1834 символа это ~250–350 элементов —
проходит. Но максимальный чанк 9 247 символов даёт порядка 800–1 200 —
то есть на масштабе создание индекса может упасть на самых длинных чанках.

**Решение при этом не меняется:** на 164 чанках sequential scan действительно
быстрее индекса, и индекс не нужен. Поправить надо комментарий — иначе на этапе 5
вы прочитаете «HNSW невозможен» и не станете пробовать, хотя достаточно обрезать
sparse-веса до топ-1000 (стандартная практика для bge-m3, качество почти не падает).

Предлагаемая замена комментария:

```sql
-- SPARSEVEC: HNSW поддерживается (sparsevec_ip_ops), IVFFlat — нет.
-- Ограничение HNSW: до 1000 ненулевых элементов на вектор (тип хранит до 16000).
-- У bge-m3 число ненулевых = число уникальных токенов чанка: медиана ~300,
-- самые длинные чанки ~1000+, то есть на масштабе индекс упрётся в лимит.
-- При 164 чанках sequential scan <#> даёт <50 мс — индекс не нужен.
-- При росте до 100k: обрезать sparse до топ-1000 весов, затем создать HNSW.
```

## 🟡 Схема: нет ключа дедупликации

**Файл:** `migrations/001_init.sql`, таблица `chunks`

Повторный запуск загрузчика продублирует все чанки. На этапе 2 вы будете
переиндексировать многократно, подбирая contextual prefix и чанкинг, — и получите
тихо растущую таблицу с дублями в выдаче.

Добавьте естественный ключ:

```sql
ALTER TABLE chunks
    ADD CONSTRAINT chunks_natural_key UNIQUE (doc_id, icode, part_index);
```

Внимание: `icode` может быть `NULL`, а `NULL` в UNIQUE не конфликтует. Либо
используйте `COALESCE(icode, heading)` через уникальный индекс по выражению,
либо пусть загрузчик делает `DELETE FROM chunks WHERE doc_id = $1` перед вставкой.
Второе проще и для полной переиндексации честнее.

## 🟡 `max_length=8192` — лишняя плата на CPU

**Файл:** `rag/embedder.py`, `encode()`

8192 — предел bge-m3, но вам он не нужен: самый длинный чанк 9 247 символов,
это ~2 400 токенов. При этом FlagEmbedding паддит батч по самому длинному
элементу, а стоимость внимания квадратична по длине — один длинный чанк
замедляет весь батч.

```python
MAX_LEN_INDEX = 2048   # покрывает самый длинный чанк (9247 симв. ≈ 2400 ток.)
MAX_LEN_QUERY = 512    # вопрос механика короткий
```

Замерьте оба варианта на реальном `chunks.json` — на индексации 164 чанков
разница должна быть заметной, а на 75 000 она превратится в часы.

## 🟢 Мелочи

**Гонка при ленивой загрузке.** `_load()` без блокировки: на этапе 3 под FastAPI
два параллельных запроса могут начать грузить модель одновременно. Одна строчка:

```python
import threading
_lock = threading.Lock()

def _load(self) -> None:
    if self._model is not None:
        return
    with _lock:
        if self._model is not None:
            return
        ...
```

**Импорт.** `from rag.config import settings` внутри пакета лучше сделать
относительным: `from .config import settings` — модуль перестанет зависеть от того,
как запущен процесс.

## Что не менять

Это сделано правильно, не трогайте при исправлениях:

- Ленивая загрузка модели вместо загрузки при импорте
- `use_fp16=False` на x86 CPU
- try/except вокруг параметра `devices` для совместимости версий FlagEmbedding
- Сериализация sparse через текстовый литерал с `::sparsevec` cast
- `control_module` как partial index с `WHERE NOT NULL`
- Отказ от индекса на sparse при текущем объёме
- Комментарии в SQL, объясняющие *почему*, а не *что*
